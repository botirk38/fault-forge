\section{Empirical Insights}
\label{sec:findings}
% ===========================================================================

Our evaluation reveals five key insights about slow-fault vulnerability in
production distributed systems. These findings have immediate implications
for system design, monitoring, and testing practice.

\subsection{Timeout Architecture Determines Resilience}
\label{sec:finding-timeouts}

The converged boundaries cluster into four distinct tiers that map directly
to each system's failure detection mechanism:

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \textbf{Raft heartbeat systems ($\leq$19.5\,ms).} etcd, ZooKeeper,
        MongoDB, TiKV, CockroachDB. These systems use aggressive heartbeat
        intervals (default 100--500\,ms) with election timeouts at
        1--10$\times$ the heartbeat. A network delay of 19.5\,ms is
        sufficient to push RTT beyond the heartbeat interval, triggering
        leader re-election. The election itself involves message
        round-trips that are \emph{also} subject to the injected delay,
        creating a cascade.
  \item \textbf{$\phi$-accrual/gossip systems (39\,ms).} Cassandra, HBase.
        These use adaptive failure detectors ($\phi$-accrual for Cassandra,
        ZooKeeper sessions for HBase) with longer baseline windows. The
        detector's suspicion level rises more gradually, requiring
        2$\times$ the perturbation to trigger.
  \item \textbf{KRaft/controlled election (78\,ms).} Kafka's KRaft protocol
        uses controlled shutdown with explicit leadership transfer,
        tolerating 4$\times$ more delay than raw Raft before the
        controller marks a broker as fenced.
  \item \textbf{Explicit timeout systems ($>$300\,ms).} Redis
        (\texttt{cluster-node-timeout}/2 = 2.5\,s for PFAIL) and Hadoop
        (NameNode heartbeat timeout). These deliberately trade detection
        latency for jitter tolerance---a conscious design choice.
\end{enumerate}

\para{Architectural implication} The 130$\times$ spread between the most
sensitive tier (19.5\,ms) and the most tolerant (2.7\,s) is a direct
consequence of timeout configuration, not implementation quality. Systems
in Tier~1 could move to Tier~4 resilience by adopting configurable election
timeouts---as etcd partially does with \texttt{heartbeat-interval} and
\texttt{election-timeout}---but operators rarely change defaults.

\subsection{Fault Type Sensitivity Varies 4--16$\times$}
\label{sec:finding-sensitivity}

Within a single system, vulnerability boundaries vary dramatically across
fault types. For etcd: network (19.5\,ms), filesystem (78\,ms), CPU (0.20
cores), memory (192\,MB). The 4$\times$ gap between network and filesystem
reflects that Raft consensus messages transit the network \emph{before}
touching disk, so network delay disrupts the critical path earlier.

For Cassandra, the gap is 8$\times$ (39\,ms network vs.\ 312\,ms filesystem)
because gossip protocol messages are small and frequent (network-sensitive)
while memtable flushes and compaction tolerate I/O stalls (filesystem-tolerant).

\para{Testing implication} Single-fault-type testing (e.g., network-only)
captures only one dimension of a system's vulnerability surface. A complete
characterization requires all fault types, but given limited budget, network
faults provide the tightest bounds for consensus systems.

\subsection{Single-Fault Testing Is Optimistic}
\label{sec:finding-multi}

Multi-fault combinations reduce individual boundaries by 22--50\% (mean 31.4\%,
Table~\ref{tab:multi-fault}). The compound effect is strongest when faults
target \emph{orthogonal resources} consumed by the same critical path:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \textbf{nw + fs (38\% reduction, etcd):} Raft heartbeat delayed on
        network \emph{and} WAL sync delayed on disk. The leader cannot
        commit entries (blocked on disk) while followers are timing out
        (blocked on network).
  \item \textbf{nw + nw on 2 nodes (38\% reduction, Cassandra):} Gossip
        protocol loses majority of its information sources simultaneously,
        causing the $\phi$-accrual detector to spike faster than with a
        single slow node.
  \item \textbf{nw + fs (50\% reduction, HBase):} RegionServer cannot flush
        WAL (fs) while its ZooKeeper session heartbeat is delayed (nw),
        causing session expiry before the flush completes.
\end{itemize}

\para{Implication for production} Real cloud environments experience
correlated degradation (e.g., noisy-neighbor CPU throttling + shared-network
congestion). Single-fault danger zones are the \emph{best case}; actual
safety margins should assume at least 30\% tighter boundaries.

\subsection{Minimization Is CI-Practical}
\label{sec:finding-ci}

\system{} characterizes a single system in 7--14 minutes wall-clock time
(17--18 iterations $\times$ 25--45\,s per trial including full Docker cluster
lifecycle). The entire 10-system $\times$ 5-fault-type matrix completes in
$\sim$8 hours on a single server---well within nightly CI budgets.

\para{Regression testing} Boundaries are stable (CV$<$5\%), so a 1-step
increase between releases (e.g., etcd boundary drops from 19.5\,ms to 9.8\,ms
after increasing election timeout) constitutes a meaningful signal. We
propose a CI assertion:

\begin{lstlisting}[language=bash,basicstyle=\ttfamily\small]
faultforge minimize --system etcd:v3.6 \
  --assert-boundary-above 15ms \
  --fault nw --oracle etcd-raft.yaml
# Exit 1 if boundary < 15ms (regression)
\end{lstlisting}

\subsection{Monitoring Must Operate at ms Granularity}
\label{sec:finding-monitoring}

The 250$\times$ gap between consensus boundaries (19.5\,ms) and production
alerting thresholds (1--5\,s) represents a \emph{monitoring blind spot}. Any
network perturbation between 20\,ms and 1\,s is simultaneously dangerous
(above the failure boundary) and invisible (below the alerting threshold).

This finding has concrete implications:
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \textbf{Network monitoring} must report P99 latency at sub-100\,ms
        resolution, not 1\,s buckets.
  \item \textbf{Failure detectors} should expose their internal thresholds
        (heartbeat interval, election timeout) as metrics, alerting when
        observed latency approaches these thresholds.
  \item \textbf{Adaptive failure detection} (e.g., $\phi$-accrual) provides
        inherent defense but is not used by the most popular systems (etcd,
        ZooKeeper).
\end{itemize}

\para{Broader context} This finding connects to the \emph{metastable failure}
pattern~\cite{bronson-metastable}: a system operating in a vulnerable state
(network latency near 19.5\,ms) can be tipped into cascading failure by a
minor additional perturbation. The gap between danger zone and monitoring
threshold is the \emph{metastability window}---the range of severities where
the system is vulnerable but no alert fires.
