\section{Discussion}
\label{sec:discussion}
% ===========================================================================

\subsection{Implications for System Design}

Our results suggest concrete recommendations for distributed system designers:

\para{Configurable heartbeat intervals} Systems should expose heartbeat
interval and election timeout as first-class tuning parameters with clear
documentation of the resilience/detection trade-off. Currently, most systems
(etcd, TiKV, CockroachDB) compile these values into binary defaults.

\para{Adaptive failure detection} Systems using fixed-interval heartbeats
(Raft-based) show the narrowest danger zones. Moving to adaptive approaches
($\phi$-accrual, sliding-window variance tracking) provides 2 to 5$\times$
wider jitter tolerance with comparable detection latency.

\subsection{CI Integration}
\label{sec:ci-integration}

Minimal recipes translate directly to CI regression tests via
\texttt{faultforge minimize --assert-boundary-above 15ms}. A weekly cron job
or pull-request trigger on consensus-related paths provides continuous
boundary monitoring. The job fails if the converged boundary drops below the
asserted threshold, enabling regression detection across versions.

\subsection{Boundary Interpretation}
\label{sec:interpretation}

The converged severity is an \emph{upper bound} on the true boundary.
For highly sensitive systems (etcd, ZK, MongoDB, TiKV), 19.5\,ms is the
precision floor ($5000/2^8$); \xinda{}'s grid confirms reproduction at
100\,$\mu$s. For operational purposes, the distinction is immaterial:
both values are below any reasonable monitoring threshold.

\subsection{Limitations}
\label{sec:limitations}

\para{Single-node injection} Production may have correlated multi-node
degradations; our multi-fault experiments partially address this.
\para{Containerized deployment} Docker eliminates real network hardware
effects; however, containers are the standard CI/development target.
\para{Workload sensitivity} Production workloads may shift boundaries.
\para{Monotonicity} Pathological workloads with timeout-based retries could
violate monotonicity; not observed in our evaluation.

\subsection{Threats to Validity}
\label{sec:threats}

\para{Internal} Non-determinism mitigated by repeated runs ($<$5\% CV)
and dense monotonicity probes ($>$97\% fidelity).
\para{External} Ten systems span Raft, ZAB, gossip, $\phi$-accrual, and
KRaft architectures in Go, Java, C, and Rust. \para{Construct} ``Boundary''
= minimal severity triggering oracle-detectable symptoms; user-visible
impact may require higher severity due to client retries.

\subsection{Toward Production Deployment}
\label{sec:production}

The \texttt{RunTrial} protocol abstracts infrastructure: a
\texttt{K8sRunner} can replace \texttt{nsenter + tc netem} with Istio
fault injection or eBPF-based delay (\texttt{tc-bpf}). Oracle rules can
match Prometheus alerting expressions rather than log patterns.

\subsection{Data Availability}

\system{} is open source. Oracle specifications, system configurations,
experiment scripts, and raw trial logs for all 50 system/fault
configurations are available in \texttt{experiments/RESULTS.md}.
