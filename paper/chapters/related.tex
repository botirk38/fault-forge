% ===========================================================================
\section{Related Work}
\label{sec:related}
% ===========================================================================

\para{Slow-fault characterization}
\xinda{}~\cite{xinda} (NSDI~'25) is the most closely related system.
\xinda{} provides an automated pipeline for characterizing slow-fault
impacts via exhaustive grid evaluation. \system{} differs in three ways:
(1)~continuous boundary estimation rather than discrete grid testing,
(2)~noise-tolerant probing via composable strategies, and (3)~multi-dimensional
minimization (severity $+$ duration $+$ timing). These are complementary:
\xinda{}'s grid provides a complete danger-zone \emph{map}; \system{}
provides precise \emph{boundary measurements} for CI integration.
Anduril~\cite{anduril} (ATC~'25) extends \xinda{} to compound faults
with performance tracing.

\para{Metastable failures}
Bronson et al.~\cite{bronson-metastable} (OSDI~'22) formalize metastable
failures: states where a system operates normally under typical load but
catastrophically fails under small perturbations. Our finding that consensus
systems fail at 19.5\,ms, invisible to monitoring, directly instantiates
the metastability pattern: the 250$\times$ gap between boundary and alerting
threshold is the metastability window. \system{}'s boundaries quantify
\emph{how close} a system operates to its metastable trigger, complementing
Bronson et al.'s qualitative taxonomy with precise measurements.

\para{Chaos engineering and fault injection}
Netflix Chaos Monkey~\cite{basiri-chaos} pioneered automated fault injection
in production. Gremlin and LitmusChaos~\cite{litmus-chaos} provide
configurable fault injection but do not minimize fault parameters.
PRE-FAIL~\cite{pre-fail} uses state-machine models to guide injection but
targets crash failures. Jepsen~\cite{jepsen} tests linearizability under
network partitions but does not characterize slow-fault boundaries.
FATE/DESTINI~\cite{gunawi-fate} (OSDI~'11) systematically injects I/O errors
in distributed storage systems using failure specification language. Unlike
\system{}, FATE targets crash-type faults (fail-stop I/O) and exhaustively
enumerates injection points rather than minimizing along a continuous severity
axis.

\para{Test-case minimization and shrinking}
Delta debugging~\cite{zeller-dd} minimizes failure-inducing inputs via binary
search over input elements. C-Reduce~\cite{creduce} extends this to
multi-pass hierarchical reduction for C programs. QuickCheck~\cite{quickcheck}
and its derivatives (Hypothesis, fast-check) use integrated \emph{shrinking}:
after finding a failing test case, the shrinker systematically reduces inputs
toward a minimal counterexample. \system{}'s greedy dimensional minimization
is conceptually analogous to shrinking, applied to the fault parameter space
rather than program inputs. The key difference is that each ``evaluation''
in our domain requires executing a full distributed system trial (25 to 45\,s),
making budget-optimal search critical; QuickCheck's shrinking assumes
millisecond evaluations.

\para{Gray failure and partial failures}
Huang et al.~\cite{huang-gray-failure} (HotOS~'17) identify gray
failures, where a component is degraded but not detected as failed, as a
major reliability challenge. Our work quantifies the boundary at which gray
becomes catastrophic: the 19.5\,ms threshold is precisely where ``gray''
(sub-threshold degradation) transitions to ``failure'' (observable system
impact). Gunawi et al.'s cloud reliability studies~\cite{gunawi-cbs,lu-cloud}
catalog failure causes but do not measure boundaries.

\para{Model checking and formal verification}
Molly~\cite{molly} and LDFI use lineage-driven fault injection to find
minimal failure scenarios in distributed protocols. Filibuster~\cite{filibuster}
applies this to microservice testing. These approaches target logical faults
(message drops, reorderings) and use SAT/SMT solvers for minimization.
\system{} targets performance faults (continuous severity parameters)
where solver-based approaches are less applicable due to the need for
real-system execution.

\para{Distributed system testing}
CrashFuzz~\cite{crashfuzz} combines crash-consistency testing with fuzzing.
Flymc~\cite{flymc} explores failure scenarios via model checking with
semantic-aware state reduction. TLA+ and P provide formal verification of
distributed protocols but cannot capture performance-sensitive timing
behavior. \system{} is complementary to these approaches: formal methods
verify protocol correctness while \system{} characterizes performance
vulnerability boundaries in real implementations.

\para{Black-box optimization}
Bayesian optimization~\cite{snoek-bayesopt} uses Gaussian process models to
efficiently optimize black-box functions. We compare against a GP-UCB-inspired
baseline in Section~\ref{sec:baselines-eval} and find that the monotone
structure of fault boundaries makes binary search information-theoretically
optimal, eliminating the benefit of GP modeling.
